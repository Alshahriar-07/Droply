How Droply works

Droply pairs two browsers with a short code, then moves the file bytes directly between them over an encrypted WebRTC data channel.

  • The sender picks files and creates a one-time room with a six-character code.
  • The receiver enters the code or scans the QR code.
  • Both browsers negotiate a peer-to-peer connection through a lightweight signaling service.
  • After the receiver accepts, file chunks stream directly between the devices.
  • The room closes when the transfer finishes, is cancelled, or expires.

What leaves your device

Only connection metadata (offer, answer and ICE candidates) reaches the signaling service. File names, sizes and contents never do. Files are decrypted only on the receiving device.

Privacy & security

  • No accounts, no sign-in and no transfer history.
  • File contents are never uploaded to Droply, Cloudflare or any storage bucket.
  • Transfers use WebRTC DTLS encryption, which is end-to-end between the two browsers.
  • Rooms are one-time, limited to one sender and one receiver, and expire automatically.
  • The receiver always sees what is being sent and must accept before any file data flows.
  • The signaling service only handles short-lived connection setup messages.

Network reality

On some networks (symmetric NAT, strict corporate firewalls) a direct route is impossible. In that case Droply reports the failure instead of silently falling back to storage. If a TURN relay is configured by the operator, encrypted WebRTC packets are relayed — never stored.

Room codes are short by design. They are rate-limited, expire quickly and only grant access to a single pending transfer, so never share a code publicly.
